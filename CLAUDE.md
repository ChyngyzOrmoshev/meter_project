# meter_project — АСКУЭ «ИнфоЭнерго»

Django-приложение для автоматизированного сбора, хранения и анализа показаний приборов учёта электроэнергии, а также удалённого управления реле.

## Важно при работе с проектом

- **База боевая.** Реальные команды **отключения** на счётчики при отладке не отправлять. Безопасно: чтение, команды `on` на заведомо включённый счётчик, запросы состояния реле. Тестовый абонент: счётчик `11848001` (Sanxing_old, «Иванов Иван»). Тестовые Hexing-счётчики: `61002510` (на связи, реле включено), `61007588` (не на связи).
- Секреты только в `app/cEnergo.env` (в `.gitignore`). Пароли в коде и в `docker-compose.yml` запрещены.
- Код смонтирован в контейнеры томом `./django_app:/app`: для применения правок Python достаточно `docker compose restart django scheduler`. Пересборка (`--build`) нужна только при смене `requirements.txt` или `Dockerfile.django`.
- Каталог `django_app/meters/migrations/` и `__pycache__` создаются от root (Docker). Миграции создавать в контейнере: `docker exec meters_django python manage.py makemigrations`.

## Стек

- Python 3.11, Django 5.2 (версии пакетов закреплены в `django_app/requirements.txt`)
- MySQL 8 (`mysqlclient`)
- Внешние источники: MSSQL (FreeTDS), PostgreSQL, MySQL
- APScheduler (единый планировщик)
- Playwright + Chromium (остался только для Hexing POP)
- pandas, openpyxl, python-calamine (для 1С)
- Docker Compose

## Архитектура

Три контейнера:

| Контейнер | Роль |
|---|---|
| `meters_mysql` | БД MySQL 8. Лимит памяти 7G (InnoDB buffer pool 5G). Порт 3306 открыт только на `127.0.0.1` |
| `meters_django` | Веб (gunicorn + whitenoise), порт 8000 |
| `meters_scheduler` | Планировщик APScheduler со всеми роботами в одном процессе |

`docker.sock` в контейнеры не монтируется. Пароли MySQL (`MYSQL_ROOT_PASSWORD`, `MYSQL_DATABASE`, `MYSQL_USER`, `MYSQL_PASSWORD`) берутся из `app/cEnergo.env` через `env_file`.

## Автотесты

```bash
docker exec meters_django python manage.py test meters --settings=config.settings_test
```

`config/settings_test.py` подменяет БД на SQLite в памяти: боевая MySQL не затрагивается, сетевых запросов нет (HTTP к 1С подменяется). Покрыты `relay_queue` (задачи в полёте, откладывание, отмена только `pending`) и `onec_service` (контракты `readdebt` и `checkdebt`, Basic в UTF-8, статусы `ok`/`Not`, локальный режим, `check_debts`). Воркер `process_relay_tasks` покрыт с заглушками провайдеров (ни одна команда не уходит): повторы 5/10/20 мин, проверка долга перед `off`, двухфазная схема Hexing/SunRise/RiseSun/cEnergo, выбор пачки и возврат зависших задач. Пул потоков в тестах заменён последовательным исполнителем. Вьюхи реле (`test_relay_views.py`): доступ по группам, ограничение по районам `ASKUE:<район>`, поиск счётчика, одиночные/массовые задачи и загрузка по списку, повтор только для `error` и только `is_staff`, монитор с фильтрами. Автовключение (`test_auto_on.py`): условия по долгу и истории, пауза после ошибки, задачи в полёте. Файл результата массовой загрузки в тестах подменяется (`views_relay.BULK_RESULT_PATH`). Импорт показаний (`test_readings_import.py`): ручной ввод, загрузка Excel (даты Excel, пустые ячейки), фоновый импорт (направление по колонке, форматы дат, ошибки по строкам, сохранение результата в сессию), старая форма `import-readings-excel`. Excel читается как текст (`read_import_excel`), иначе даты не сериализуются в JSON-сессию, а серийники с пустыми ячейками становятся `61002510.0`. Десятичная запятая в значениях (`12,5`) не поддерживается, строка попадает в ошибки. Расчёт баланса (`test_balance_calculator.py`): коэффициенты ТТ×ТН с историей и `end_date`, показания на дату, границы декад и месяца, баланс по фидерам (отдача A− вычитается, кэш результатов). Иерархия из 1С (`test_hierarchy_sync.py`): ключи, правила привязки, дерево. Дубли `BalanceResult` и фильтр диаграмм баланса покрыты в `test_balance_calculator.py`. Дополнительно покрыты: снимки ЛС/ФИО/долга в задачах и мониторе (счётчики кнопок-фильтров, поиск по ФИО), состояние SunRise «готов к включению» и автопроверка через 6 ч, запрет отключения счётчиков 5А (`CtMeterTests`, `CtMeterViewsTests`), сохранение долга из 1С при отмене, автовключение через 1С (`AutoOn1CTests`). Робот Kaifa (`test_sync_kaifa.py`): повторы, код ошибки в теле ответа, постраничность, сопоставление приборов; запись в `readings` идёт MySQL-запросом `ON DUPLICATE KEY UPDATE`, на SQLite не выполняется (заменён заглушкой), реальная запись проверена только живым запуском. Поиск по кириллице без учёта регистра в SQLite не работает (в боевой MySQL работает): в тестах брать тот же регистр. 330 тестов, около 11 секунд. Новый код реле и 1С нужно сопровождать тестами; правки проверять на «мутациях» (намеренно сломать код и убедиться, что тест падает).

`/api/v1/devices/`, `/api/v1/devices/<serial>/`, `/api/v1/readings/`, `/api/v1/readings/latest/` (`meters/api_v1.py`, маршруты в начале `urls.py`). ### Kaifa — отдельное задание раз в 2 часа (:50)

| Команда | Время | Источник | Примечание |
|---|---|---|---|
| `sync_kaifa` | каждые 2 часа в :50 | Kaifa MDM | HTTP API, суточные данные (`PTCAP`, запись на 00:00), ~20 сек |

Вне быстрой цепочки намеренно: сервер Kaifa временами не завершает SSL-рукопожатие, и его зависание блокировало бы остальных роботов (цепочка идёт с `max_instances=1`). Приборы докладывают в течение дня (на 24.11 пришло 42 183 записи за сегодня, остальные за 22–23 ноября), поэтому нужен повторный сбор.

- Приборы: `askue_id='30'`, `api_id='KF'` (около 46 тыс., все активные); робот берёт только активные. Серийники на сервере совпадают с нашими точно (проверено: 42 241 строка из 42 241), нормализация не нужна. Часть приборов (около 4 тыс.) в выгрузке региона `KAIFA_REGION_ID` отсутствует.
- Запрос: `/api/mdm-service/measure/row-data-report/query`, `recordsMode=LAST` (одна последняя запись на прибор в окне `--days`, по умолчанию 2), `profileType=DAILY`. **`pageSize` не больше 1000**: на 5000 сервер отвечает HTTP 200, но в теле `code: 500` и `data: null`. Любая ошибка сервера приходит в теле, поэтому `_request` проверяет `code`.
- Устойчивость: таймауты соединения 15 сек и чтения 60 сек, 3 попытки с паузой 5 и 10 сек, общий потолок 15 минут. При сбое на странице уже сохранённое остаётся, статус робота `error`.
- Запись: `direction='aplus'`, `notes='Авто-сбор: Kaifa'` (эта заметка есть в `AUTO_NOTES` дашборда), `SyncStatus` с `robot_name='Kaifa'` (карточка на дашборде, перезапуск кнопкой работает через `restart_robot`).
- Отладочный `test_kaifa_data` ходит на сервер без таймаутов и может зависнуть, не запускать при тормозящем Kaifa (зависший процесс в контейнере останавливается только изнутри).
- Не подключено: автоматическая регистрация новых приборов из Kaifa (`registration.py`) и опрос по кнопке (`readings_fetcher.py`).

### Обслуживание и реле (задания планировщика)

- `auto_close_issues` — каждый час в :10.
- `check_debts_auto_on` — каждые 10 минут: автоматическая постановка задач на включение для оплативших абонентов (проверка долга через 1С, окно 14 дней, см. «Автовключение»).
- `process_relay_tasks` — каждую минуту: воркер очереди реле (см. ниже).
- `warm_dashboard_cache` — каждые 10 минут («сегодня») и раз в час в :20 с `--all` (3d/7d/30d): пересчёт статистики дашборда и карточек районов за один проход в общий файловый кэш (`CACHES` в `settings.py`, каталог `django_app/cache/`, в `.gitignore`). Расчёт идёт одним запросом «устройства с показаниями за период» и агрегацией в Python: 2–8 секунд на период (раньше до 35). В тот же кэш пишется список приборов без показаний за период (`get_no_reading_ids`, с датой): отчёты `/missing-readings/`, `/readings-with/` и `/reports/device-types/` фильтруют по нему (`report_helpers.filter_by_period` берёт более короткий из двух списков), поэтому новые приборы появляются в них с задержкой до 10 минут. Вьюхи `dashboard`, `region_stats_table` и `producer_stats_table` (без `region_id`) только читают кэш (`dashboard_stats.py`; в кэше данные, а не HTML), при пустом кэше считают сами.

## ⚡ Управление реле (Remote Control)

Страница `/relay-control/`: вкладки «Реле» (одиночное управление), «Задачи» (массовые), «Мониторинг» («Очередь задач»).

### Доступ и ограничения

- Доступ: `is_staff` или группы `operator` / `Инженер АСКУЭ` (`can_manage_relay`). Кнопка «Повтор» задачи — только `is_staff`.
- Группы `ASKUE:<район>` (название района ровно как в `Region.name`, например `ASKUE:03 Сузак`) ограничивают инженера своим районом. Проверка `relay_region_denied` стоит в статусе, действии, массовом создании задач и загрузке по списку: чужой счётчик или счётчик без района для ограниченного пользователя закрыт (403). Админы не ограничены.
- Поиск счётчика (`find_relay_device`): точное совпадение, иначе однозначное совпадение по окончанию номера (без ведущих нулей, не короче 5 символов). Пустой или неоднозначный номер счётчик не выбирает.

### Мониторинг («Очередь задач»)

- Данные: `relay_task_monitor_data` (`/relay-control/api/tasks-monitor/`). Кнопки-фильтры со счётчиками (Все, Успешно, Ошибка, Ожидание, Отменено, Отключения, Включения): счётчики приходят в `counts` и считаются по периоду, району и поиску, без учёта действия и статуса. Поиск — по серийнику, ЛС, ФИО (из задачи и из `Subscriber`). Данные грузятся при открытии вкладки, затем автообновление раз в 10 секунд.
- В `RelayTask` хранятся снимки на момент постановки: `debt_snapshot`, `account_snapshot`, `name_snapshot` (миграция 0032; из 1С, при её отсутствии — из `Subscriber`). Для задач на включение без своих данных ЛС/ФИО берутся из последней задачи на отключение (`last_off_snapshot`). Тип ПУ и ампер берутся из `Device.model` (в таблице должников — из ответа 1С, иначе из базы).
- Пояснение под строкой (`note`): отменённые задачи (причина), «ждёт кнопку» (SunRise), текст ошибки. При отмене из-за оплаты в `debt_snapshot` записывается долг, который вернула 1С (может быть отрицательным — переплата).
- Оформление: общий стиль темы (`.rq-*` в `theme.css`: матовое стекло, Urbanist/Jost, капсулы, тёмно-синий акцент).

### Счётчики 5А (через ТТ)

Физически отключить нельзя, поэтому задачи `off` на них не создаются. `is_ct_meter` (`relay_queue.py`): максимальный ток в скобках `nominal_current` ≤ 10 А (`5(10)`, `1/5(10)`) или «CT» в названии модели; без модели — не 5А (в базе под правило попадает около 4500 из 137 тыс. приборов). Проверка стоит в одиночном действии (409), массовом создании (счётчик пропускается, в итоге пишется количество), загрузке по списку (ошибка) и воркере (страховка: `off` отменяется). В UI бейдж «5А ТТ» и предупреждение в окне подтверждения. Включение разрешено.

### Создание задач

- **Одиночное** (`/relay-control/api/action/`): создаёт `RelayTask` на «сейчас». Прежние ожидающие задачи счётчика отменяются, а «задачи в полёте» нет (см. ниже): новая встаёт после них. Если такая же команда уже в полёте — 409. Команды view напрямую не шлёт: выполнит воркер в течение минуты.
- **Массовое** (`/relay-control/api/mass-create-tasks/`): список должников приходит из 1С (`OneCService.get_debtors`). Сервер проверяет `action` (`on`/`off`), обязательное и корректное время (минимум +30 минут; UI требует +1 час), пропускает чужие районы и дубли (такая же активная задача уже есть). Противоположные ожидающие задачи отменяются, задачи в полёте не трогаются (новая встаёт после них). Для счётчиков, найденных в 1С, но отсутствующих в АСКУЭ, создаются заявки `CompareResult` (`not_found`).
- **По списку номеров** (`/relay-control/bulk-start/`, результат в `/relay-control/bulk-status/`): для каждого номера создаётся `RelayTask` (отключение — на «сейчас + 30 минут», включение — сразу). Прямых команд нет. В интерфейсе вызова нет, доступен только запросом.
- **Повтор** (`/relay-control/api/task-retry/`): только для `error`; сбрасывает `retry_count` и `hexing_payload`.
- **Автовключение** (`check_debts_auto_on`): кандидаты — счётчики, у которых последняя запись `RelayCommandHistory` — `off` со статусом `success`/`pending` не старше `OFF_WINDOW_DAYS` (14 дней; более старые не проверяются). Долг проверяется пачками по `CHECK_BATCH` (100) через `OneCService.check_debts` (`known_debts`: счётчик, которого нет в ответе 1С, пропускается, а не считается оплатившим); для районов без 1С — по локальному `Subscriber`. Долг ≤ 0 — отменяются ожидающие задачи на отключение и создаётся задача на включение (ЛС/ФИО из задачи отключения). После упавшей (`error`) задачи на включение счётчик пропускается `RETRY_PAUSE_HOURS` (6 ч), чтобы не создавать задачи каждые 10 минут.

### Задачи в полёте (`relay_queue.py`)

`inflight_tasks` — задачи, команда по которым уже ушла или уходит: `processing`, а также `pending` с заполненным `hexing_payload` (первая фаза пройдена, ждём проверку итога). `supersede_tasks` отменяет только прочие `pending`. Если по счётчику есть задача в полёте, новая откладывается: минимум на 2 минуты (`BUSY_DELAY_MIN`) или на минуту после времени второй фазы (`PHASE2_GAP_MIN`); для cEnergo это около 12 минут. Используется в ручном управлении, массовом создании, загрузке по списку и автовключении.

### Воркер очереди (`process_relay_tasks.py`)

- Каждую минуту берёт до 50 задач `pending` с наступившим `scheduled_at` (`select_for_update(skip_locked)`), переводит в `processing`, выполняет в 5 потоках.
- **Проверка долга перед отключением:** запрос в 1С (`OneCService.check_debts`); для района без базы 1С или без `ONEC_SERVER_URL` — локальный `Subscriber`. Долг ≤ 0 — задача `cancelled`, в задачу записывается ответ 1С (`debt_snapshot` и текст причины). Если 1С недоступна — отключать нельзя, задача идёт в повтор.
- **Повторы:** при ошибке 1-я повторная попытка через 5 минут, 2-я через 10, 3-я через 20; после этого `error`.
- **Готов к включению (SunRise):** состояние 2 после `on` — не ошибка: задача `success` с пометкой `READY_NOTE`, счётчик ждёт нажатия кнопки на нём. Кнопка «Кнопка нажата» в мониторе (`/relay-control/api/task-confirm-button/`) перечитывает состояние и снимает пометку (при несовпадении можно подтвердить вручную). Через `READY_EXPIRE_HOURS` (6 ч) воркер сам перепроверяет состояние (`expire_ready_tasks`).
- **Зависшие задачи:** `processing` старше 30 минут (`STUCK_TIMEOUT_MIN`) возвращаются в `pending`.
- В `RelayCommandHistory` пишется `user = task.created_by`. Ошибки в историю не пишутся (только `success`/`pending`), они видны в `RelayTask.error_message`.

### Системы счётчиков и двухфазная схема

Поток воркера не держится «спящим» в ожидании. Для систем с асинхронным итогом после отправки команды задача возвращается в очередь (`pending`, новое `scheduled_at`), а состояние хранится в JSON-поле `RelayTask.hexing_payload` (название историческое, поле общее для всех систем; `provider` внутри JSON). Вторая фаза проверяет итог. Если не подтвердилось — ошибка и обычные повторы с повторной отправкой команды (для отключения долг проверяется заново). Долг на второй фазе не перепроверяется.

| Система (askue_id / api_id) | Отправка | Проверка итога |
|---|---|---|
| Hexing KUK (25 / UK) | REST `/switch`, ACK `2001` | Через 125 сек (`HEXING_RESULT_DELAY_SEC`) повторный `/switch` тем же XML (`check_pending`). Успешный сценарий проверен в бою (команда `on` на счётчик 61002510, задача завершилась за ~4 минуты); путь ошибки не проверялся |
| SunRise (26 / SR) | REST, CIM XML (GZIP+Base64) | Раз в минуту читается реальное состояние реле (`nativeData=1`; 0 — отключено, 1 — включено, 2 — готово к включению, ждёт кнопку), до 5 минут (`SUNRISE_WAIT_MIN`). Таймаут HTTP-запросов 45 сек (`API_TIMEOUT`): сервер сам опрашивает спящий счётчик |
| RiseSun (24 / RS) | MMWS REST, пакет `disconnect-batch` / `reconnect-batch`, один `Idempotency-Key` на все сетевые повторы | Раз в минуту `GET /disconnect-batch/{id}` (единый статус для обеих операций), итог по `items` (`done`/`failed`, коды ошибок по APIDOC), до 15 минут (`RISESUN_WAIT_MIN`). Проверено только на заглушках |
| cEnergo (23 / EM) | SOAP `SetMeterState`, `sync_timeout` 60 сек | При `TimeoutExpired` (счётчик спит) cEnergo сама повторяет команду каждые 5 минут в течение 10 минут (настройка сервера cEnergo, `CENERGO_WINDOW_MIN`), затем «Сбой отправки команды управления реле» (`SetMeterStateFailed`). Через 11 минут воркер читает `GetMeterState` (1 — включён, 2 — отключён) |
| Sanxing_old (22 / SX) | HTTP, `/realtimereading/index/switch`, логин с капчей через ddddocr | Синхронно: `errorCode == 0` — выполнено, `Off line(code:-2)` — счётчик офлайн (повтор). Чтения состояния реле нет |

Только cEnergo держит команду на своём сервере; остальные системы команды не удерживают, поэтому после ошибки старая команда позже не выполнится.

Код ошибок cEnergo расшифровывается в `cenergo_service.ERROR_TEXTS`, RiseSun — в `risesun_service.ERROR_TEXTS`.

## 🔗 Интеграция с 1С

- `OneCService` (`onec_service.py`): `get_debtors(region, min_debt)`, `check_debts(region, meters)`, `known_debts` (только счётчики, присутствующие в ответе) и `has_1c(region)`. `checkdebt` не возвращает ЛС и ФИО, они берутся из `readdebt` или из задачи. База 1С выбирается по району (`ONEC_DB_*`); для районов без базы (ЖПЭС) и без `ONEC_SERVER_URL` данные берутся из локальной таблицы `Subscriber`.
- Контракт 1С (`1С_API.txt`, не в git): HTTP-сервис `POST {ONEC_SERVER_URL}/{база}/hs/askue/readdebt` (путь строчными), тело `{"min_debt", "askue_types"}`, Basic-авторизация (`ONEC_USER`/`ONEC_PASSWORD`; логин кириллический, заголовок собирается вручную в UTF-8). Ответ: `status: ok` + `data` (`serial_number`, `account_number`, `full_name`, `debt`, `askue_type_id`) или `status: Not` (должников нет).
- Проверка долга по списку: `POST .../hs/askue/checkdebt`, тело `{"meters": [{"serial_number", "askue_type_id", "askue_type_str"}]}` (`askue_type_str` — `Device.api_id`: SX/EM/RS/UK/SR), ответ `status: ok` + `data` (`serial_number`, `askue_type_id`, `debt`). Счётчика нет в ответе (или `status: Not`) — долг 0, отключение отменяется. Недоступность 1С или другой статус — исключение и повтор. Серийники сравниваются без ведущих нулей.
- `ONEC_DB_OVERRIDE` (например `proba83`): пробная база заменяет базы **всех** районов (при заданном `ONEC_SERVER_URL` в том числе ЖПЭС без своей базы; `has_1c` в этом случае истина). Для боевого режима удалить из `cEnergo.env`: иначе серийников там нет и все отключения отменяются. После правки `cEnergo.env` нужен `docker compose up -d --no-deps --force-recreate django scheduler`: `restart` не перечитывает `env_file`.
- `Subscriber`: лицевой счёт, ФИО, долг, привязка к `Device`.
- `CompareResult`: заявки. Если 1С присылает должника, а в АСКУЭ его нет — заявка `not_found`.
- Иерархия из выгрузок 1С (`hierarchy_sync.py`, в `sync_1c_statuses` под `--apply`): колонки «ТП», «Фидер», «Подстанция» (необязательная) → `Device.tp/feeder/substation`, 1С главнее (пустое значение ничего не стирает). Правила привязки:
  - **Без допустимой ТП прибор не получает ничего** (ни ТП, ни фидера, ни подстанции). Допустимы только значения на «ТП-» (`usable_tp`); «АС 341», «ТГ 355» и т. п. игнорируются.
  - **Фидер — пара «название + подстанция».** Поиск ограничен районом. Если подстанции в строке нет, её подсказывает ТП (`tp_main_sub`), затем единственная подстанция, где такой фидер уже есть. Неоднозначный фидер без подсказки не выбирается; существующие фидеры между подстанциями не переносятся.
  - ТП без фидера: служебная подстанция «Не определена» и фидер «Не определен» (в районе).
  - Ключи (`tp_key`, `feeder_key`, `substation_key`): регистр, латиница/кириллица, пробелы, «ТП», «ВЛ», «10 кВ», «ф.» не важны; «/» сохраняется. Отсутствующие объекты создаются.
  - Отчёты: `updated_hierarchy.csv`, `hierarchy_created.csv`, `hierarchy_duplicates.csv`, `new_meters.csv` (серийники из 1С, которых нет в АСКУЭ).
- Страница `/sync-1c/` и команды `sync_1c_statuses`, `verify_1c_issues`; выгрузки 1С лежат в `1c_reports/` (в `.gitignore`).

### Реле
- **Hexing:** успешный сценарий проверен на счётчике 61002510 (`on` на включённый счётчик; физического переключения не наблюдали). Вторая фаза при повторном `pending` считает задачу успешной; лучше подтверждать по `get_relay_status_from_db` (проверить на отключённом счётчике). Путь ошибки не проверялся: для него годится 61007588 (в БД Hexing нет статусов реле, похоже, не на связи).
- **RiseSun:** схема написана по черновому регламенту (APIDOC «проект для согласования»), проверить на реальном MMWS одной командой `on`. `DISCONNECT_NOT_SUPPORTED` повторяется впустую три раза.
- **SunRise:** `MessageID` и дата в XML-заголовке зашиты (`2026-10-29`), команды при этом проходят. Значение состояния 2 («готов к включению») принято по DLMS и подтверждено только скриншотом счётчика; живой ответ API с `value=2` не наблюдали.
- **5А:** граница правила (ток в скобках ≤ 10 А или «CT») выведена из `nominal_current`; уточнить у заказчика.
- Задачи до миграции 0032 остаются без ЛС/ФИО/долга в мониторе (снимков нет).
- Для боевого режима убрать `ONEC_DB_OVERRIDE` и пересоздать контейнеры.
